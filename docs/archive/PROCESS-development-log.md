# Process overview

Campus Poster Studio began with a question about campus notices: a visitor should be able to find an event without first being asked to make an account, while the small group organising that event needs a way to make the poster together. I therefore chose a public poster wall as the application entry point and made creation an optional second path. This distinction changed the early concept from a private design tool into a small campus publishing space.

The first delivery uses a small Node HTTP service and browser JavaScript rather than a full framework. The course deployment provides one small machine and a durable `/data` volume. A JSON data store on that volume is enough to prove the core interaction and makes the persistence boundary visible. If the project grows beyond the pilot, SQLite is the likely next step because it retains the single-machine deployment model while providing transactions and more reliable concurrent writes.

The application has three persistent objects: posters, canvas elements, and comments. A poster has a university label, owner display name, publication state and canvas elements. Published posters are returned to guests by university; drafts use the same object while the editor is open. This deliberately small schema lets the project prove that a visitor can create a poster, publish it, then return to see the result before adding accounts, uploads or moderation.

Real-time delivery uses server-sent events. Saving an edit or comment writes the durable record first and then broadcasts a small event to open pages. This means the database remains the source of truth: a browser that reconnects can request the current poster rather than relying on a missed event. The initial editor demonstrates text, coloured shapes and dragging. Its next design task is to add element-level editing presence and invitation permissions; it should not claim to be a complete Canva replacement.

The README's definition of good led to concrete rules in `CLAUDE.md`: guests can browse, university labels do not imply verification, and public posters change only through an explicit publish action. The supplied HTTP checks verify that the app and README route remain deployed. The next specifications will cover publication visibility, draft persistence and the distinction between saved and published content.

## CampusWall implementation — 1 October 2026

The expanded product specification required real authentication, private drafts and invited collaboration. The initial pilot could not enforce ownership because display names were chosen in the browser. The implementation keeps the small Node service and the public `/readme/` route but replaces that identity model with password hashes and persistent, expiring HTTP-only sessions. All editing and lifecycle actions now check the account on the server.

SQLite on the existing `/data` volume replaces the JSON runtime store. An additive, versioned migration creates universities, users, posters, collaborator relationships, comments and sessions. Existing JSON data is retained and copied into a legacy archive; published legacy notices remain public. Anonymous legacy drafts cannot safely be assigned to someone who merely chooses the same display name, so their original records are preserved without exposing them to new accounts.

The public campus wall remains the entry point. Guests select a university, filter or search published notices, open details and read comments. Creation uses five constrained templates and structured event fields. Published notices retain a snapshot while the private working copy can change; only the creator can republish the accepted working copy.

WebSockets replace the pilot's global event stream for editing. Each draft connection must authenticate and pass a creator-or-collaborator access check. Field updates are validated and committed before broadcasting a new monotonically increasing version. Different-field changes survive together; same-field updates use server acceptance order. Reconnect sends the authoritative saved state. Connection loss explicitly reports unsaved changes, rather than silently treating a local copy as saved. Presence comes from active connections, heartbeat timeouts and room departure.

The automated product test starts an isolated server and checks 18 scenarios with three accounts and two independent WebSocket clients. It includes forbidden HTTP and socket access, creator-only actions, concurrent edits, comment validation, migration privacy, live revocation, reconnection, a server restart and session invalidation. The supplied HTTP invariants and TypeScript checks remain in place. Browser checks additionally cover the guest-to-create login return, template selection, saving, publication and responsive layouts. These checks establish functional behaviour; real student use is still needed to judge whether notices are useful and clear.
